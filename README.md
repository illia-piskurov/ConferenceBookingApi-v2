# Тестове завдання ConferenceBookingApi

---

## Архітектура

Я вирішив обрати Controller-based API замість Minimal API, оскільки в тестовому завданні явно було прописана вимога:
"Використовуйте практики з книги "Чистий код" Robert Cecil Martin під час написання рішення. Проєкт в майбутньому буде
розширюватися, тому важливо, щоб він був масштабованим, безпечним та відмовостійким." За принципами з книги, кожен класс має відповідати за одну річ,
тому використав класичне розподілення на контроллери, сервіси та репозиторії. Оскільки явної вимоги до використання бази даних в тестовому завданні не було,
поки зробив просте in-memory зберігання, але завдяки інтерфейсу та розділенню, можна легко додати підтримку реляційної бази даних (sqlite, postgresql, тощо).
Також перевагою є що сервіси можна тестувати окремо, підставляючи моковані репозиторії.

У продакшн-версії API має бути захищене за допомогою JWT Bearer authentication або API Key. Для тестового завдання вирішив поки не робити автентифікацію.

## Endpoints

### Зали (`/api/rooms`)

| Метод    | Шлях                   | Що робить                                |
| -------- | ---------------------- | ---------------------------------------- |
| `GET`    | `/api/rooms`           | список всіх залів                        |
| `GET`    | `/api/rooms/{id}`      | один зал по ID                           |
| `POST`   | `/api/rooms`           | створити зал (з послугами)               |
| `PUT`    | `/api/rooms/{id}`      | оновити зал                              |
| `DELETE` | `/api/rooms/{id}`      | видалити зал                             |
| `GET`    | `/api/rooms/available` | пошук вільних залів за часом і місткістю |

### Бронювання (`/api/bookings`)

| Метод  | Шлях                          | Що робить                       |
| ------ | ----------------------------- | ------------------------------- |
| `POST` | `/api/bookings`               | створити бронювання             |
| `GET`  | `/api/bookings/{id}`          | отримати бронювання по ID       |
| `GET`  | `/api/bookings/room/{roomId}` | всі бронювання конкретного залу |

### Звіти (`/api/reports`)

| Метод | Шлях                      | Що робить                            |
| ----- | ------------------------- | ------------------------------------ |
| `GET` | `/api/reports/revenue`    | виручка за період (по днях)          |
| `GET` | `/api/reports/popularity` | рейтинг залів по кількості бронювань |
| `GET` | `/api/reports/load`       | завантаженість залів у відсотках     |

## Технічні рішення

### Зберігання — ConcurrentDictionary

Дані живуть у `ConcurrentDictionary<Guid, Room>` та `ConcurrentDictionary<Guid, Booking>`.
ASP.NET Core обробляє кілька HTTP-запитів паралельно. Звичайний `Dictionary` при одночасному записі з двох потоків може "зламатись", тому взяв потокобезпечний `ConcurrentDictionary`.

Методи репозиторіїв повертають `Task`, хоча код синхронний. Це зроблено для сумісності з майбутньою реальною БД — там все асинхронне. `Task.FromResult(value)` загортає синхронне значення у Task.

При запуску `DataSeeder` заповнює сховище початковими залами з послугами.

### Розрахунок ціни — цінові зони

`PricingService` не рахує вартість просто `години × ставка`. Він розбиває інтервал на цінові зони і рахує кожну частину окремо:

| Зона             | Час           | Множник |
| ---------------- | ------------- | ------- |
| Ранкова знижка   | 06:00 – 09:00 | ×0.90   |
| Стандарт (ранок) | 09:00 – 12:00 | ×1.00   |
| Пік              | 12:00 – 14:00 | ×1.15   |
| Стандарт (день)  | 14:00 – 18:00 | ×1.00   |
| Вечірня знижка   | 18:00 – 23:00 | ×0.80   |

Вартість послуг — фіксована сума за одне бронювання, додається поверх вартості залу.

### Захист від подвійного бронювання

Перевірка перетинів і збереження — **дві окремі операції**. Між ними є вікно, де два паралельних запити обидва можуть пройти перевірку і обидва зберегтись, створивши конфлікт.

Погуглив, використав `SemaphoreSlim(1, 1)` — семафор, що пропускає лише один потік одночасно в критичну секцію "перевірка + збереження". Семафор `static` — спільний для всіх екземплярів сервісу.

Формула перевірки перетину двох інтервалів `[A_start, A_end)` і `[B_start, B_end)`:

```
перетин є, якщо: A_start < B_end AND A_end > B_start
```

Дві бронювання "впритул" (перша закінчується о 12:00, друга починається о 12:00) — конфлікту немає.

### Валідація бронювання

Перед збереженням перевіряється:

- час початку < час кінця
- не можна бронювати в минулому (`start < DateTime.UtcNow`)
- максимальна тривалість — 24 години
- зали працюють з 06:00 до 23:00

> дати передавати з суфіксом `Z` (UTC), наприклад `"2026-08-01T09:00:00Z"`. Без timezone .NET парсить як `DateTimeKind.Unspecified`, і порівняння з `DateTime.UtcNow` може дати несподіваний результат.

### Обробка помилок — GlobalExceptionHandlerMiddleware

Для обробки помилок використовується middleware `GlobalExceptionHandlerMiddleware`, який перехоплює всі виключення і повертає відповідний HTTP-статус.

```json
{
  "status": 404,
  "error": "Зал із ID '...' не знайдено.",
  "timestamp": "2026-07-28T19:00:00Z"
}
```

| Виняток                       | HTTP статус               |
| ----------------------------- | ------------------------- |
| `RoomNotFoundException`       | 404 Not Found             |
| `BookingConflictException`    | 409 Conflict              |
| `InvalidBookingTimeException` | 400 Bad Request           |
| Все інше                      | 500 Internal Server Error |

Middleware має бути першим у pipeline — щоб ловити помилки з усього ланцюжка.

## Запуск

```bash
dotnet run
```

Swagger UI: [http://localhost:5254](http://localhost:5254)

Тестові запити: `ConferenceBookingApi.http` (VS Code + розширення REST Client).

> **Нюанс .http-файлу:** після оновлення залу (`PUT`) сервіси отримують нові GUID-и. Тому перед бронюванням з послугами — виконай `GET /api/rooms/{id}` щоб отримати актуальні serviceId.
